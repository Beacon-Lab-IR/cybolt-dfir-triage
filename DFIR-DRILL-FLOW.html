DFIR Drill · KAPE-MEDIA v5.2.14

Flujo de adquisición forense
sobre hipervisor VMware

Procedimiento operativo para adquisición de evidencia digital en VMs Windows comprometidas (ransomware / intrusión). El disco de salida viaja entre tres VMs mediante re-attach del VMDK; la red permanece aislada durante toda la captura. Cadena de custodia preservada porque los archivos nunca abandonan el disco de evidencia hasta la entrega final.

vSphere 7/8 + ESXi ~30–50 min total Cadena de custodia intacta Sin red durante captura

01Flujo de 4 etapas

El disco de evidencia (DFIR-OUTPUT.vmdk) viaja entre las VMs como medio de transporte forense. Cada re-attach preserva timestamps NTFS, $MFT, $LogFile, $UsnJrnl y ADS—copiar a SMB y de vuelta los mutaría.

Adquisición

VM-A (infectada)

3
Notas. Anotar extensión del ransomware, wallpaper, ransom note, servicios caídos. Quedan en E:\\NOTES\\.

02Artefactos generados

Todo queda en DFIR-OUTPUT.vmdk durante la captura. El VMDK es el contenedor forense, no los archivos sueltos.

Path en E:\\ (DFIR_OUTPUT) Contenido Generado por Tamaño típico
RAM-{HOST}-{YYYYMMDD-HHMMSS}.raw RAM Volcado físico de RAM (procesos vivos, conexiones, credenciales en memoria) RAM_CAPTURE_UI.exe / winpmem ~RAM asignada
RAM-{HOST}-...raw.sha256 HASH SHA-256 del .raw para verificar integridad en análisis RAM_CAPTURE_UI.exe 64 bytes
{HOST}-KAPE-{YYYYMMDD-HHMMSS}.zip KAPE KapeTriage: registry hives, $MFT, event logs, prefetch, scheduled tasks, Amcache, $LogFile, $UsnJrnl, etc. KAPE_TRIAGE_UI.exe / kape.exe ~800 MB
{HOST}-KAPE-...zip.sha256 HASH SHA-256 del ZIP KAPE_TRIAGE_UI.exe 64 bytes
NOTES\{HOST}-NOTES-{YYYYMMDD}.txt CONTEXTO Notas de la corrida: extensión del ransomware, wallpaper, ransom note, usuarios afectados Operador (durante el drill) ~2 KB
NOTES\{HOST}-LOG-{YYYYMMDD}.txt CONTEXTO Log completo de KAPE_TRIAGE_UI.exe (6 fases, hashes, tiempos) KAPE_TRIAGE_UI.exe ~10 KB

03Comandos VMware (ESXi shell / SSH)

Equivalentes CLI a las acciones del vSphere Client. Útiles cuando el host ESXi está aislado o para automatizar.

Etapa 2 · Shutdown limpio

Apagar VM-A desde la CLI del ESXi. Requisito: VMware Tools instalado en guest.
# Listar VMs y su ID
vim-cmd vmsvc/getallvms | awk 'NR==1 || $1 ~ /VM-A/'

# Shutdown limpio (no power-off)
vim-cmd vmsvc/power.off $(vim-cmd vmsvc/getallvms | awk '$2=="VM-A"{print $1}')

# Esperar a poweredOff
while [ "$(vim-cmd vmsvc/power.getstate <vmid>)" != "Powered off" ]; do sleep 5; done

Etapa 2 · Detach disco

Remover el VMDK de VM-A sin borrarlo del datastore. -1 en SCSI = quitar disco 2.
# Ver configuracion actual
vim-cmd vmsvc/device.getdevices <vmid-A> | grep -A3 "scsi0:1"

# Remover disco (mata el device, conserva el .vmdk)
vim-cmd vmsvc/device.conn -usb <vmid-A> 2>/dev/null  # refresh
# vSphere Client: Edit Settings → SCSI(0:1) → Remove (no Delete)

Etapa 3 · Attach a VM-B

Mismo datastore, distinta VM. Existing disk apunta al -flat.vmdk.
# Agregar disco existente a VM-B
vim-cmd vmsvc/device.diskadd <vmid-B> m \
  "[datastore1] DFIR-OUTPUT/DFIR-OUTPUT.vmdk" \
  0 1 scsi

# Alternativa: editar .vmx de VM-B y agregar:
scsi0:1.present = "TRUE"
scsi0:1.fileName = "DFIR-OUTPUT.vmdk"
# (respetar path relativo al datastore)

Etapa 3 · Verificar integridad

Desde VM-B, una vez montada la ISO y el VMDK como read-only.
# En PowerShell dentro de VM-B
Get-ChildItem E:\RAM-*.raw, E:\*KAPE-*.zip |
  Get-FileHash -Algorithm SHA256 |
  Format-Table

# Comparar contra los .sha256 companion
Get-Content E:\RAM-*.raw.sha256
Get-Content E:\*KAPE-*.zip.sha256

Etapa 4 · Copia al datastore IR

Mover el par VMDK al datastore compartido del equipo IR o NAS de custodia.
# Desde ESXi shell (datastore origen)
cp /vmfs/volumes/datastore1/DFIR-OUTPUT/DFIR-OUTPUT*.vmdk \
   /vmfs/volumes/datastore-IR/INCIDENT-2026-09-28/

# O vCenter Storage vMotion
# (mantiene el VMDK atomico, recomendado si hay red
#  entre hosts)

Etapa 4 · Hash del VMDK completo

Opcional pero recomendado: SHA-256 del VMDK completo para detectar cambio de bits en custodia.
# En el ESXi (donde vive el VMDK)
sha256sum /vmfs/volumes/datastore-IR/INCIDENT-2026-09-28/DFIR-OUTPUT.vmdk
sha256sum /vmfs/volumes/datastore-IR/INCIDENT-2026-09-28/DFIR-OUTPUT-flat.vmdk

# Tiempo esperado: 1-5 min por archivo de 16 GB.

04Decisiones clave del flujo

¿Por qué mover el VMDK y no copiar a SMB?
Una copia a SMB y luego de vuelta mutaría timestamps NTFS, $MFT, $LogFile, $UsnJrnl y ADS. El VMDK es el contenedor forense — viaja íntegro entre VMs. Solo en la etapa 4 (entrega) sale de allí.
¿Por qué capturar RAM antes de KapeTriage?
KapeTriage toca el filesystem en lectura pero KAPE abre handles, escribe .kape, monta VSS, etc. Capturar RAM antes preserva procesos vivos, conexiones, y credenciales en memoria del estado más cercano al incidente. Después, KapeTriage recolecta artefactos persistentes.
¿Por qué shutdown limpio, no power-off?
Power-off forzado deja el journal NTFS con operaciones pendientes sin flush. El analista vería timestamps de "last mount" corruptos. Shutdown limpia el journal antes de apagar.
¿Por qué mount read-only en VM-B?
Cualquier escritura (incluso mount normal) actualiza $LogFile y $MFT last-access times. Arsenal Image Mounter o FTK Imager con opción read-only preserva timestamps originales — el analista trabaja sobre una vista estática de la evidencia.
¿Por qué la ISO viaja con el disco?
En VM-B (análisis) el operador puede necesitar Tools\kape.zip para correr EvtxECmd/MFTECmd, o releer el MANUAL_OPERATIVO. Montar el mismo ISO evita arrastrar binarios sueltos. La ISO es read-only por definición (CD-ROM).
¿Qué pasa con la red?
VM-A: sin red durante captura (la ISO no necesita red y el ransomware no puede exfiltrar). VM-B: red opcional para descargar definiciones (YARA, IOC feeds), pero el VMDK debe estar montado read-only. VM-C / datastore entrega: red abierta, fuera del segmento de producción.
